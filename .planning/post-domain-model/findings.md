# 发现记录

- 当前仓库没有 Spring Boot 业务源码或数据库迁移模块；根 Maven 工程仅聚合文档模块。
- 原型已覆盖五类帖子：拼单、拼车、线下组队、线上开黑与近邻互助。
- 既有产品文档给出四类协作帖的关键详情字段，近邻互助另有时效、报酬、紧急度和游客脱敏要求；仍需统一公共字段、必填规则及可持久化的数据类型。
- 业务规则要求人数、支付状态和活动状态独立；发布后费用、地点或时间变更需要触发业务通知。
- 公共字段至少包括类型、标题、描述、状态、作者、可见范围、校园、发布/截止时间、地点快照、媒体和参与方式；精确地点及联系方式必须具备受控展示边界。
- 四类协作帖要求：拼单的商品与交付，拼车的路线与座位，线下组队的集合与活动要求，线上开黑的平台与开局要求；近邻互助还要求时效窗口、报酬和紧急度。
- 原型 `Activity` 将 `detail`、`distance`、时间、费用等业务值混为展示字符串，不能用于时间范围、金额、距离、席位、隐私和变更通知的可靠处理。
- 悬浮助手当前使用统一的“主题、时间、地点或线上方式、人数规则、费用或报酬”五字段，缺少按类型收集商品/交付、路线/上车点、活动要求、游戏平台、近邻时效等必要数据。
- 当前近邻互助已具备报酬、即时/时段、需求时间、最晚响应和加急的原型字段，但需要使用金额最小货币单位、`LocalDateTime` 和可验证时间窗口替换展示字符串。
- 用户指定数据库实体设计以 Oracle 为基准，仅保留逻辑类型、长度、精度、非空和关系，不输出 MySQL 方言 DDL。
- 系统设计校验发现首版跨模块模型还需独立承载登录设备、收藏、邀请奖励、兑换码及使用记录、配送轨迹、商品评价、客服反馈；已补充对应实体，避免把历史状态压缩进用户或订单主表。
- 系统设置文档要求位置精度、个性化推荐、活动资料可见性和免打扰时段，已补充到 `qh_user_preference`；订单配送已增加可选 `order_item_id` 以支持多包裹履约。
- Oracle 脚本校验：共 56 张表，0 个 `FOREIGN KEY`、0 个 `REFERENCES`，所有关系通过 `_id` 字段表达；跨表状态机与权限仍由应用服务校验。已补充帖子人数、金额、时长、库存、订单/支付金额、消息媒体和配送轨迹的字段级检查约束。
- 产品规划仍定义用户转卖为基础能力，首期页面尚未展开流程；已按最小边界补充转卖刊登与媒体实体，并令订单项通过 `source_type/source_id` 承接自营 SKU 或转卖刊登，未擅自加入议价、担保等规则外能力。
- 当前原型允许助手和社区表单在必填字段不完整时保存草稿，不能直接落入 `qh_post` 及其非空的类型扩展表；已独立为 `qh_post_draft`，正式发布转换由应用服务执行字段校验。
- 当前原型的最近搜索、小程序自定义分组、分享、推荐筛选和浏览行为不能仅依赖收藏或推荐内容事件承载；已分设搜索历史、分组、小程序关联、分享链接及行为事件实体。热门搜索应由行为事件离线聚合，不维护为可手工改写的业务明细。
- `qh_content_event` 仅适用于推荐曝光/点击/转化；运营和敏感业务操作需要独立不可变的 `qh_operation_audit_log`，但帖子、订单、积分和配送等领域状态仍以各自专用流水为准，避免审计日志成为业务事实唯一来源。
