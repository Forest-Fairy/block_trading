# 发布分期规划

## 目标

为趣汇大众 C 端应用建立系统发布分期规划，明确各期业务功能、必备基础设施、阶段准入条件与跨期依赖，并回写产品文档导航。

## 阶段

- [x] 初始化持久化计划并确认文档入口
- [x] 沿产品文档导航读取项目定位与现有模块能力
- [x] 形成发布分期、基础设施分层与优先级判断
- [x] 回写项目级发布规划及导航摘要
- [x] 校验文档链接、内容一致性与工作区差异

## 决策记录

- 采用“基础设施先行 + 业务能力分批验证”的发布方式，不将增长或商业化能力视为首发前置条件。
- 规划将以现有“趣汇”本地社区、拼拼贴、组队、求助与商城场景为边界。
- 发布顺序采用“受控内测 -> 单区域公开 -> 跨区域扩张 -> 规模化优化”，将支付履约推迟到区域公开阶段，避免在治理、客服和回滚能力未建立时扩大资金与安全风险。
- 系统管理员、运营管理员、区域管理员三类 Web 后台能力属于 R1 发布前置；区域化精细运营编排和增长能力仍在 R3 扩展。
- 大众 C 端补充能力按风险分期：未成年人保护、反滥用、应急、规则版本和无障碍在 R1；评价、争议证据、关键通知与补偿在 R2；数据生命周期与灾备在 R3；关联反欺诈、算法治理和侵权处置在 R4。
- 商城真实交易的物流跟踪、节点异常监测、履约工单与补偿/售后衔接属于 R2 发布硬性前提。
- 搜索、推荐、列表、详情、深链和缓存必须在 R1 由服务端先执行校园/地区/对象范围与拉黑关系过滤；校园版仅显示当前校区用户发布内容，任一方拉黑后双方隔离用户资料、内容和互动。
- 已按 R1-R4 完成增量实体设计：复用既有核心表，分期新增/扩展区域 RBAC、审核链、可见性失效、交易履约、数据治理、封禁与模型治理实体。
