# 调研发现

## 已知上下文

- 项目产品定位及产品文档导航入口由 `PROJECT.md` 指向。
- 本次产物需要落在正式产品文档目录，并同步更新对应导航文件。

## 已确认能力与风险

- 项目首期业务覆盖社区协作、近邻互助、自营商城、支付、订单与消息，包含陌生人社交、线下活动、精确位置和资金履约风险。
- 现有模块已规划账号安全、注销、隐私偏好、陌生人消息控制、举报拉黑、内容审核、业务通知、订单售后和在线客服入口。
- 地区能力当前主要用于位置展示、范围筛选、配送范围、校园可见性和近邻互助；需升级为可配置的区域准入、规则、生效时间与运营素材能力。

## 分期判断

- 所有对外发布前必须先具备：环境与配置隔离、灰度/回滚/功能开关、监控告警、审计与数据治理、账号隐私、内容与交易风控、地区运营配置和客服处置闭环。
- 受控内测先验证发现、发布、参与与消息闭环；区域公开后才开放真实商城支付与售后；跨区域后再引入精细化运营、推荐与实验；规模化阶段建设自动化风控、增长和商业化能力。
- 用户明确将“R0”指代当前编号体系中的第一期 R1；帖子审核和举报内容审核须于 R1 建设，审核顺序固定为规则匹配、大模型、人工审核；账号封禁分级在 R4 建设。
- 用户确认系统管理员、运营管理员、区域管理员三类后台管理能力亦须在 R1 上线；后台管理需要独立功能文档承载，不能只在项目规划中概述。
- 对现有规划的缺口盘点显示：未成年人保护、反自动化滥用、安全应急、规则版本和完整无障碍应随 R1 前置；交易公开后的履约评价、争议证据、关键通知送达与补偿在 R2；数据生命周期和灾备在 R3；关联反欺诈、算法治理和侵权处置在 R4。
- 商城文档此前仅定义待发货/待收货状态，缺少承运商运单、物流事件、异常阈值、人工履约工单与争议期；已确认为 R2 真实交易前置能力。
- 校园版现有规则对本人和关注关系保留了跨校内容，与用户要求的“校园版不看非校园帖子”冲突；已收紧为当前校区用户发布内容唯一可见范围。拉黑原仅在会话中表达，现扩展为全链路双向隔离，并要求服务端与索引/缓存失效保障。
- 既有 Oracle 核心脚本已定义账户、帖子、订单、支付、配送、售后、评价、举报、拉黑和客服基础实体；分期实体设计采用增量表与字段增强，避免重复定义既有聚合根。

## 跨期实体兼容性审查（2026-08-13）

- R1 的区域树、RBAC、审核链、可见性失效和审计基线是正确方向，但核心帖子、用户、订单、商品和工单尚未统一保存业务发生时的 `region_id` / 策略快照；若直接进入 R2/R3，会导致区域数据权限、经营归因和历史回放依赖地址文本或当前配置。
- `qh_product_sku` 的库存和价格为全局单行，需在 R2 以“区域可售报价 + 区域库存 + 履约路由”增量聚合承接，订单固化履约区域、报价和路由快照；不能到 R3 再从全局库存拆分历史。
- `qh_support_ticket` 缺少区域、优先级、SLA、分派/转交事件，R1 已承诺区域客服工单，R2 的 `qh_fulfillment_work_order` 不能替代通用客服工单。
- R3 的多区域指标、实验和删除/留存能力要求 R1/R2 事件保留区域、校区、渠道、策略/实验版本、同意状态和数据分类；当前 `qh_content_event` 与媒体 URL 记录不足以恢复历史归因或执行精确的数据主体请求。
- R4 的封禁、反欺诈和模型治理依赖早期不可变风险观察与业务事件，而 `qh_user_login_device` 仅保留最后登录状态。应在 R1/R2 采集最小化、可脱敏、可关联的风险事件和证据摘要；`qh_user.account_status` 不应承担后续细粒度封禁状态。
