# 审查发现

## 基线

- R1 为受控内测：区域准入、三段审核、后台 RBAC、可见性、用户保护与客服。
- R2 为单区域公开交易：支付、订单、区域库存、物流、售后和关键通知。
- R3 为跨区域运营：区域模板、指标、实验、数据生命周期与灾备。
- R4 为规模化优化：封禁、反欺诈、模型治理、权益与侵权处置。

## 待验证问题

- R1 的区域、工单、审计、权限和异步基础是否足以承接 R2 真实交易。
- R2 的订单、库存、支付、物流和通知事实是否足以承接 R3 多区域经营、数据治理和实验。
- R3 的区域指标、留存、实验和删除机制是否足以承接 R4 自动化风控、算法和商业化治理。

## R1 -> R2 审查结果

- 可直接复用：`qh_region`、区域 RBAC、不可变管理员审计、审核案/阶段/证据、规则/模型版本、可见性失效任务、政策版本与用户确认。它们能够承接 R2 的区域开关、商品合规、资金审批、交易证据和后台数据权限。
- 必须在 R1 预埋：统一区域解析与业务发生时区域快照。R1 的帖子和用户资料只有校园或文本地区，R2 的订单、区域库存、配送和区域看板不能用当前用户资料或收货地址文本反推归属。
- 必须在 R1 预埋：区域服务责任与路由模型。`qh_region_business_policy` 是能力开关，不表示客服、售后、配送责任人和生效期；R2 支付开通条件需要可审计的责任归属。
- 必须在 R1 补齐：`qh_support_ticket` 的区域、优先级、SLA、队列、分派/转交事件和用户通知关联。R2 的履约工单可关联但不能替代通用客服状态。
- R2 增量实现即可：区域 SKU 可售/报价、库存、锁定流水、订单履约/价格/规则快照、支付回调与对账、物流事件幂等、履约异常和通知投递历史。前提是 R1 已提供区域和异步事件契约。
- 必须约束：R1 的通知确认仅表示用户已读/确认，不可被 R2 当作关键消息送达；R2 需使用独立投递尝试、备用渠道和幂等键记录。

## R1、R2 -> R3 审查结果

- 可直接复用：R1 的区域树、角色授权、审核规则版本、可见性审计、用户政策确认，以及 R2 的支付回调、对账差异、价格快照、物流异常/履约工单、关键通知投递。R3 可在其上新增区域健康度、实验和数据治理表。
- R1 必须在发布时预埋：用户/内容/参与/客服等业务发生时的区域与校区归属快照。用户资料的城市、地区和学生认证均会变化，不能作为 R3 留存、供给、举报率与单位服务成本的历史归因来源。
- R1 必须在发布时预埋：统一的数据资产标识、数据分类、主体关联和留存类别。帖子/聊天/商品媒体目前仅保存 URL；R3 的删除、导出、法律保留与备份恢复将无法覆盖已产生的媒体和证据。
- R1 应预埋：事件的渠道、客户端、请求、区域/校区、可见性策略版本等上下文。现有内容事件只有内容、行为、推荐位置和筛选摘要，无法支持 R3 的城市/校区/渠道比较。
- R2 必须完成：订单、支付、退款、履约、库存分配和服务路由的区域/策略/责任快照。仅在价格快照存 `region_id` 不足以解释某笔订单的履约归属、区域关停、成本和 SLA。
- R2 必须完成：商品可售、库存、配送范围和营业时间的版本化生效与回滚记录；`qh_region_business_policy` 的泛型 JSON 不应成为经营策略、库存和服务 SLA 的唯一历史来源。
- R3 增量实现即可：区域规则模板、模板继承/覆盖、配置发布流水、实验定义与分桶。前提是所有生产决策都记录实际生效模板/策略版本，且实验曝光事件关联分桶；不要求把 R1/R2 历史行为伪造为实验样本。
- P2：现有邀请关系只能记录单一邀请人，缺少渠道、活动、落地页、区域和归因窗口。R3 可新增独立归因事实表，但 R1/R2 历史只能归为“未归因”，无法做精细渠道比较。
- P2：R1 的通知偏好只覆盖总开关和静默时段。R3 做分区域触达与频控前应增加按通知目的、渠道、区域和政策版本记录的订阅/撤回事实；否则只能从 R3 开始合规地精细运营。

## R1、R2、R3 -> R4 审查结果

- 可直接复用：R1 的审核阶段、规则/模型版本、人工结论、临时措施、申诉、管理员审批与审计；R2 的订单、支付回调、对账、物流异常、售后证据和评价争议；R3 的区域健康度、数据主体请求、留存策略、灾备演练、实验定义与分桶。它们分别是 R4 风控证据、商业化事实和模型治理护栏的正确基础。
- R1 必须完成：对内容、举报、登录、设备、邀请和风险挑战采集最小化且不可变的事件/证据摘要。`qh_user_login_device` 仅保留最后登录状态，`qh_risk_challenge` 只记录挑战结果；R4 无法据此重建多账号、设备或反复违规关联的证据时间线。
- R1 必须完成：统一媒体资产登记、内容摘要、对象归属、删除状态和受控访问引用。帖子、聊天、商品媒体目前主要为 URL，R4 的侵权投诉、反通知、相似图片识别和证据保全无法可靠关联既有资产。
- R2 必须完成：支付、退款、收货地址、物流、评价和优惠/积分动作的风险事件接口及可解释关联键；键应为最小化、去标识化引用，不把明文地址、支付凭据或设备标识写入风控图谱。
- R3 必须完成：实验实际曝光、策略版本、分桶、护栏触发和人工暂停的不可变事件。只有实验定义与分桶不足以证明 R4 的排序、价格、风控或权益策略经过对照实验并可关闭。
- R3 必须完成：数据主体请求与留存策略之外的“对象级法律保留/证据冻结”关系。R4 封禁申诉、侵权投诉或资金争议中的证据，不能因普通删除请求或过期清理而消失；同时应记录合法依据和解冻时间。
- R3 必须完成：会员/积分权益的不可变账本与策略快照。`qh_user_membership` 的余额/等级是投影，现有积分流水没有幂等键、区域/权益策略版本、到期或冲正关联；R4 的优惠、积分兑换、反刷补贴和申诉不能只依赖可变余额。
- R4 增量实现即可：封禁案件、风险关联图谱、模型决策审计、侵权投诉/反通知和复杂权益策略。前提是其只写入独立案件/决策/账本表，不回写覆盖 `qh_user.account_status`、订单状态、审核阶段或早期事实。
- 必须保留：封禁作用域不得拦截订单、退款/售后、申诉、隐私与注销访问；所有自动化处置需关联模型/规则版本、输入摘要、人工覆盖、关闭开关和区域/策略上下文。
