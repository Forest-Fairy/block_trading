# 服务领域边界与模块 API 重规划

## 目标

基于趣汇 R1-R4 产品生命周期、核心/分期治理实体设计，先完成服务领域分析和边界定义；随后独立审查领域边界；同时参考 spray-codex 的模块 API 边界规范重构 DDD/六边形模块规划；最后以审查结论复核系统架构和代码架构的一致性。

## 阶段

- [x] 提取产品生命周期、实体设计、现有架构和参考模块规范的边界证据
- [x] 完成服务领域分析并记录正式领域边界文档
- [x] 委派独立子智能体审查领域边界并收集调整建议
- [x] 按审查结论和 spray-codex API 边界规范重构模块规划
- [x] 回检系统架构与代码架构，记录必要调整并完成校验

## 决策原则

- 领域边界先于模块命名；模块和运行时只能表达已确认的领域所有权。
- 业务源码跨模块只依赖公开 API；通信选择由运行时 Boot 装配，不让 Adapter 互相依赖。
- R1 采用模块化单体，领域 API 在本地实现；R2-R4 服务拆分只替换通信 Adapter，不改变用例 API 和事件 Schema。
- 以聚合不变量、写入权、事务一致性、生命周期、数据保留和团队责任判断边界，不按页面或数据库表数量机械拆分。
- 不生成业务代码或 Maven POM；本轮只调整产品与架构规划文档。
