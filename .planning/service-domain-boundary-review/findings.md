# 调研发现

## 生命周期与实体证据

- R1 的强制闭环是社区发布/参与、三段审核、区域后台、可见性与拉黑、通知客服；R2 才新增真实支付、库存、物流和售后；R3 才增加区域实验、增长与数据治理；R4 才开启封禁分级、图谱和模型自动化。
- 核心实体明确 `qh_post` 是社区聚合根；订单、支付、履约、售后和评价拥有独立生命周期；`qh_report` 是多态治理提交；通知内容和收件人状态分离。
- 分期实体明确审核结论只由对象所属领域提交状态；交易域拥有订单、支付和库存事实，履约域不得直接修改支付事实；封禁案件只限制互动，不能阻断订单、售后、申诉、隐私和注销。
- 跨期事实必须固化区域/校园、策略版本、责任路由、请求关联和历史快照。投影、索引、缓存、推荐候选和分析数据不是权限或交易事实来源。

## 现有架构的有效约束

- R1 是模块化单体加 Worker，后续按业务容量和责任边界拆部署，不以周期名义强制拆微服务。
- 业务状态使用 Oracle + Outbox 原子写入，审核、通知、索引、物流、分析等跨域协作走幂等事件。
- 当前系统架构已规定审核域输出结论而非改内容状态，风控域输出信号/建议而非直接永久封禁。

## spray-codex 模块 API 规范的可复用规则

- Reactor 逐级聚合，父 POM 仅承担构建继承/聚合，不能被业务模块依赖。
- 可独立复用的业务模块拆为 `*-api`、`*-adapter`，只有真实独立部署时才增加 `*-boot`。
- 跨模块源码只依赖被调用模块 API；本地、远程、消息和测试 Stub 的通信 Adapter 仅由 Boot 装配，禁止业务 Adapter 互相依赖。
- 外部入口只能通过接口层 Adapter 调用下层 API；API 表达用例、读写分离，并要求 request/idempotency、trace、操作者等上下文。

## 模块重规划结果

- 代码规划已从“上下文 core 整包可被依赖”更新为四层逐级 Reactor；每项业务能力以 `*-api` 作为跨模块唯一编译边界，并以 `*-adapter` 承载本地/协议/技术实现。
- 运行时 Boot 在 R1 仅保留用户 API、管理 API、Worker 和 Edge Gateway 四个共享组合根；按领域 Boot 只在独立部署触发后新增。
- 领域事件按生产领域归属，避免统一契约模块演化成没有所有者的全域 DTO 包。

## 架构预审差异

- 现有系统架构将“可见性、搜索与推荐”及“分析与数据治理”合并为单一模块，和新版独立写入权存在术语差异。
- 现有系统架构把 `qh_report` 放在“社区与参与”实体列；新版边界归属于 moderation，社区只提供举报目标对象。
- 现有系统架构的运行形态、Outbox、审核/风控不直接改主状态、交易/履约分离等核心约束与新版一致。

## 独立领域审查结论

- 必须把 discovery 的权限执行改为“召回前可见性约束 + 返回前逐项复核”，禁止仅在返回前过滤。
- 高危审核临时措施需要目标领域幂等执行 API、执行回执和失败关闭；新内容默认待审不可见，既有内容控制失败时必须安全降级。
- R2 拼单结算必须由 commerce 唯一拥有订单/库存/支付/退款；community 的参与支付字段只能作为交易事件驱动的资格投影。
- 原 `analytics-growth` 必须拆为 R1 即落地的 `growth-benefits` 和 R1 采集、R3 完整启用的 `analytics`。
- 上下文快照与 Outbox 是每个领域在自身事务/逻辑 schema 中写入的共享技术契约，governance 只消费审计/留存索引。
- 需对齐举报归 moderation、评价文本违规归 moderation 协作而订单资格/争议归 fulfillment，并补充履约状态回传给 commerce 的协议。
- 审批工作流/审计属于 governance，区域策略版本与生效/回滚属于 region-policy；模型目录/版本/准入需独立为 model-governance，业务领域仅保存调用决策。
- identity 拥有年龄验证/监护同意，trust-safety 拥有风险挑战和安全事件，region-policy 提供区域应急路由，engagement 只负责通知。
