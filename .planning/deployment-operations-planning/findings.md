# 检查发现

## 已确认规则
- `PROJECT.md` 指定系统架构与部署规划入口为 `block_trading_docs/产品文档/项目文档/趣汇系统架构设计/navigator.csv`。
- 项目规则规定部署脚本和环境资产归属 `block_trading_deployment`，不得放入 Boot 或领域模块。
- 产品文档必须使用 `content.md + navigator.csv` 双文件，并逐级维护导航摘要。

## 待核查
- 自动化部署是否具有脚本入口、环境参数、幂等/回滚、健康检查和验收定义。
- 后台日志追踪与筛选是否具有查询字段、权限、脱敏、导出或追踪链路约束。
- 日志月度归档、按日期/大小切片是否区分在线日志与归档介质，并具备保留/清理规则。
- 数据库是否支持以部署号绑定目标实例/服务名/Schema、迁移版本和审计记录。

## 初步覆盖判断
- 自动化部署已有骨架：系统架构规划了 Docker/Kubernetes、灰度与回滚；代码模块规划写明部署资产包含镜像、`k8s/base`、环境 overlay、迁移顺序及部署/灰度/回滚脚本。
- 现有部署规划仍偏目录级，没有定义统一入口脚本、部署号参数、前置校验、幂等重跑、失败退出码、回滚边界、部署记录和端到端验收。
- 现有可观测性写到 OpenTelemetry、Prometheus、Grafana、日志脱敏和统一 `request_id`，但未发现后台日志追踪/筛选能力，以及月归档、日期/大小切片、保留与清理策略。
- 数据库仅出现 Oracle 与按领域逻辑分 Schema，部署资产提到“迁移执行顺序”，未发现“按部署号指定目标数据库/Schema/迁移版本”的明确参数契约。
- 命名存在冲突：项目规则要求部署脚本和环境资产归 `block_trading_deployment`，现有架构正文使用 `quhui_deployment`；应按项目规则统一并同步 `PROJECT.md` 的目标根模块清单。

## 前缀调整范围
- 精确搜索到 11 个正式文件包含 `quhui_`，包括 `PROJECT.md`、项目/功能规划、R1-R4 需求 CSV、测试用例和社区协作业务模块文档。
- 统一替换规则为 `quhui_` -> `block_trading_`，不处理无下划线的品牌、包名或外部术语。
- 已完成 12 个正式文件的替换；全仓排除 `.git`、`node_modules`、`dist`、`.planning` 后精确反查结果为零。

## 已采用的规划口径
- `block_trading_deployment` 升级为明确的目标根模块，实际创建后进入 Maven Reactor；`block_trading_client` 仍为唯一不进入 Maven Reactor 的目标根。
- deployment_no 格式为 `DEP-{yyyyMMdd}-{4位序号}`，引用不可变 YAML 清单；数据库通过 datasource_ref + Oracle service/schema + migration baseline/target 解析。
- 日志使用逐行 JSON，在线文件在自然日边界或达到默认 100 MiB 时滚动；默认在线 30 天、月归档 12 个月，治理保留优先。
- 后台原始日志默认只允许具备 `operations:log:read` 的系统管理员访问，普通运营管理员和区域管理员默认禁止。
- 自动化部署采用 validate -> migrate -> deploy -> verify -> active 流程，失败可幂等重试、回滚或终止；不提供任意 JDBC URL/明文凭据入口。
