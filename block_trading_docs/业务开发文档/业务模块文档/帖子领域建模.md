# 业务模块文档：帖子领域建模

## 建模范围

本模型覆盖拼单、拼车、线下组队、线上开黑和近邻互助的草稿、审核、发布、参与、媒体、地点与字段变更审计。评论、举报和订单沿用各自领域模型，只通过 `post_id` 关联。

## 设计决策

采用“帖子主实体 + 公共从实体 + 类型扩展实体”模型，而不是单张超宽表或 JSON 业务载荷：

1. `Post` 保存所有类型均需检索的状态、可见范围、招募人数与主时间。
2. `PostLocation`、`PostMedia`、`PostParticipant` 分别保存可复用的一对多关系。
3. 每个业务类型使用一张一对一扩展表，保证金额、时间、人数和路线可以校验、排序与建立索引。
4. 精确地点和联系方式不写入公开 DTO；地点行通过 `visibility_level` 控制成员可见性。

字段设计以 Oracle 逻辑类型为准，但不绑定具体 DDL、序列或触发器实现。完整字段长度、精度和实体关系位于 `block_trading_docs/数据库设计/帖子领域实体设计.md`。

## 核心实体关系

```text
Post 1 ── * PostMedia
Post 1 ── * PostLocation
Post 1 ── * PostParticipant
Post 1 ── * PostChangeLog
Post 1 ── 1 GroupBuyPost | CarpoolPost | OfflineTeamPost | OnlineTeamPost | NeighborHelpPost
```

`PostParticipant.join_status`、`payment_status` 与 `Post.status` 三者独立更新；不能以是否付款推导是否加入，也不能以是否已达标推导支付状态。

## 公共字段矩阵

| 字段 | Java 类型 / Oracle 逻辑类型 | 必填性 | 规则与页面表达 |
|---|---|---|---|
| `id` | `Long` / `NUMBER(19)` | 系统必填 | 雪花或序列主键；不在页面显示。 |
| `postType` | `PostType` / `VARCHAR2(32)` | 必填 | 五类枚举；发布首步选择，之后不可跨类型修改。 |
| `title` | `String` / `VARCHAR2(60)` | 必填 | 2-60 字；列表标题和详情标题。 |
| `content` | `String` / `VARCHAR2(2000)` | 可选，近邻互助必填 | 补充说明；详情“发起人备注”。 |
| `status` | `PostStatus` / `VARCHAR2(32)` | 系统必填 | 草稿、审核中、招募中、已达标、进行中、已完成、已满员、已取消、已超时。 |
| `visibilityScope` | `VisibilityScope` / `VARCHAR2(16)` | 必填 | `PUBLIC` 或 `CAMPUS`；由校园模式给默认值。 |
| `campusId` | `Long` / `NUMBER(19)` | 条件必填 | 范围为 `CAMPUS` 时必填；只用于服务端过滤。 |
| `joinMode` | `JoinMode` / `VARCHAR2(16)` | 必填 | `DIRECT` 或 `APPLICATION`；对用户显示“立即参与/申请加入”。 |
| `currentParticipants` | `Integer` / `NUMBER(5)` | 系统必填 | 初始为发起人计数；列表和详情人数进度。 |
| `minParticipants`、`maxParticipants` | `Integer` / `NUMBER(5)` | 协作帖必填 | `1 <= min <= max`；近邻互助固定为 1，不要求用户输入。 |
| `primaryOccursAt` | `LocalDateTime` / `TIMESTAMP(6)` | 必填 | 活动开始、出发或需求时间；列表时间排序。 |
| `signupDeadlineAt` | `LocalDateTime` / `TIMESTAMP(6)` | 必填 | 拼单为下单截止，协作帖为报名截止，互助为最晚响应；表单基于主时间预填且可编辑。 |
| `createdAt`、`publishedAt`、`updatedAt` | `LocalDateTime` / `TIMESTAMP(6)` | 系统必填 | 审核、排序和审计。 |

金额统一使用货币最小单位 `Long amountCent`（如 `8600` 表示 ¥86.00），不得以浮点数或“约 ¥86”字符串持久化。日期时间统一为带时区解释的业务本地时间入参，服务端落库为 UTC；DTO 返回 ISO-8601 时间与展示文案分离。

## 简洁发布策略

发布页仅显示“必填基础信息”和“当前类型必填信息”，控制在 5-7 个控件内：

1. 标题与关键时间为公共首屏字段；地点默认使用当前市区，不要求输入精确地点。
2. 人数由两个数字输入组成，仅拼车、线下组队和线上开黑显示；拼单只收目标人数，互助不显示人数。
3. 精确地点、规格、行李限制、成员要求、退款/取消规则、语音要求和补充说明收在“更多说明（可选）”。
4. 截止时间从主时间预填，用户只在需要时修改；可见范围从校园模式预填，不强制重复选择。

## 索引与一致性

- `qh_post` 建立 `(status, post_type, primary_occurs_at)`、`(visibility_scope, campus_id, status, published_at)`、`(author_id, status, updated_at)` 索引。
- `qh_post_location` 建立 `(district_code, latitude, longitude)` 索引；生产环境可替换为数据库地理空间索引。
- `qh_post_participant` 对 `(post_id, user_id)` 唯一，避免重复参与；对 `(user_id, join_status, updated_at)` 建索引。
- 发布、加入、退出和人数变更必须使用乐观锁 `version`；达到人数上限时在同一事务内校验并更新。
- 修改 `primary_occurs_at`、`signup_deadline_at`、金额、地点或参与要求时写入 `PostChangeLog`，由业务通知领域消费。

本模块不新增运行时接口；发布、草稿和详情接口在服务端模块创建后按本字段模型定义。
