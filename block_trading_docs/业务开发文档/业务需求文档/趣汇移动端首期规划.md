# 需求文档：趣汇移动端首期规划

## 需求背景

趣汇需要同时支持 Web、Mobile 和 Micro-app。首期先完成移动端产品基线，底部固定“推荐、社区、商城、消息、我的”五个页面，并为后续小程序与 Web 复用账户、内容、订单和消息模型。

## 需求目标

- 推荐页以信息流分发社区、商城和未读通知。
- 社区页覆盖购物拼单、出行拼车、线下组队和线上开黑。
- 商城页支持公司自营产品的浏览和购买。
- 消息页按系统通知、业务通知、用户消息的顺序组织。
- 我的页按个人信息、更多趣汇小程序、兑换码、偏好设置的顺序组织。
- 输出可用于前端实施的规划文档、交互说明和高保真原型。

## 用户故事

1. 作为普通用户，我希望在推荐页快速看到附近可参与的活动、商城新品和重要未读状态。
2. 作为活动发起人，我希望按拼单、拼车、线下组队或线上开黑类型快速发布，并清楚看到人数和截止状态。
3. 作为参与者，我希望在加入前了解费用、时间、地点、当前人数、最少/最多人数和退出规则。
4. 作为商城消费者，我希望确认商品来自趣汇自营，并完成可靠的下单和售后。
5. 作为消息接收者，我希望优先处理平台安全和业务状态，再查看用户沟通。
6. 作为账户持有人，我希望在个人中心查看业务记录、使用兑换码并管理偏好设置。

## 首期范围

| 页面 | 必须具备 |
|---|---|
| 推荐 | 综合信息流、兴趣筛选、搜索、未读摘要、三类卡片 |
| 社区 | 分类、筛选、列表、详情、发布、参与、分享、状态表达 |
| 商城 | 分类、商品列表、详情、购物车、确认订单、支付状态 |
| 消息 | 两个固定通知入口、用户会话列表、未读和消息设置 |
| 我的 | 个人信息、四个业务快捷入口、更多趣汇小程序、兑换码、偏好设置和退出登录 |

## 关键业务规则

- 社区内容必须属于购物拼单、出行拼车、线下组队或线上开黑之一。
- 拼车和线上开黑必须同时维护当前人数、最少人数和最多人数，不能用单一固定人数替代。
- 参与人数、支付状态和活动状态分别记录，避免相互覆盖。
- 推荐页的社区、商城和通知内容必须显示明确类型。
- 趣汇小程序列表每次只查询一次接口，按 `onlyCurrentGender` 过滤；排序按收藏、显式排序值（空值靠后）、使用频次、流量热度执行，并记录查询时间，超过 1 分钟重新获取。
- 系统通知固定在消息页第一项，业务通知固定在第二项。
- 我的页面中“更多趣汇小程序”位于个人信息之后、兑换码之前，标题右侧显示“探索更多 >”；兑换码仍位于偏好设置之前，个人资料不展示用户编号。
- 学生认证区域位于“我的”页面底部，退出登录固定为最后一项；认证信息仅当前用户可见，完成认证后才可切换校园版。校园版开启时新帖子默认仅同校可见，推荐、搜索和社区列表除本人及关注用户发布外仅展示同校区内容。
- 未登录用户可以浏览，发布、参与、支付和发送消息时要求登录。

## 非功能要求

- 移动端基准尺寸为 390×844px，并兼容常见安全区。
- 核心触控区域不小于 44×44px。
- 所有页面覆盖加载、空数据、失败和业务结束状态。
- 社区线下活动需要隐私保护、举报和拉黑能力。
- 校园版筛选需要使用 `campusId`，帖子需要记录 `visibilityScope`；商城商品和系统通知不受同校区过滤影响。
- 原型使用 React、TypeScript、Tailwind CSS、shadcn/ui 和 Lucide 实现。
- 原型修改后必须截图复核布局、层级、状态和可读性。

## 验收标准

1. 五个一级页面均有完整默认态高保真原型。
2. 底部导航顺序、选中状态和消息未读徽标一致。
3. 推荐页能够区分社区、商城和通知三类卡片。
4. 社区页明确呈现四类业务及人数、时间、地点关键字段。
5. 消息页严格按系统通知、业务通知、用户消息排序。
6. 我的页面严格按个人信息、更多趣汇小程序、兑换码、偏好设置排序，且不展示用户编号。
7. 学生认证、校园版开关和仅同校可见默认范围可操作且说明清晰；列表过滤遵循本人、关注用户、同校区例外规则。
8. 文档导航能够从项目文档逐层定位到功能和模块内容。
