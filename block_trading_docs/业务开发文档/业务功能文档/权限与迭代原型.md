# 业务功能文档：角色权限与迭代原型

## 对应需求

本功能承接移动端首期规划中的账户、校园版与运营管理能力，并将权限规划拆分为 R1-R4 可演示原型状态。

## 账户与 RBAC

- 游客是未登录访问主体，不创建 `qh_user`，只能浏览明确允许公开的系统信息。
- 所有已登录用户均使用同一 `qh_user` 账户并从 `VIP_1` 起始；VIP 等级只影响权益与配额。
- `SYSTEM_ADMIN`、`OPERATION_ADMIN`、`REGION_ADMIN` 是附加在 `qh_user` 上的 RBAC 角色。鉴权同时校验资源、动作、数据范围、有效期、状态和高风险二次验证。
- 三类管理员均在用户端“我的 -> 设置”显示受服务端能力清单控制的入口，并进入对应的响应式移动管理界面。
- 三类管理员同时可从独立 PC Web 后台入口登录；移动端与 PC 端共用 `qh_user`、角色授予和服务端能力清单，PC 端不是独立账户体系。

## 权限模板基线

生产鉴权固定采用 Casbin `RBAC with Domains` 模板：`qh_user.user_id` 作为主体，`region_id` 作为 domain，资源和动作作为策略对象。系统与运营角色使用全局 domain，区域管理员授权必须带具体 `region_id`；每个 API 在服务端执行裁决，客户端和后台只使用返回的能力清单渲染入口。Kotlin 工程实现时必须选用兼容该模型的 Casbin 执行器与持久化 Adapter，并以 `qh_admin_role_grant` 作为角色授予事实来源。

## 原型页面关系

```text
原型控制区 -> 迭代与访问主体
区域管理员/运营管理员/系统管理员 -> 我的 -> 设置 -> 对应移动管理界面
三类管理员 -> 独立 PC Web 后台入口 -> 对应角色工作台
```

`src/prototype/access.ts` 维护演示会话与权限结果；`CommerceFlowPage.tsx` 维护游客交易预览和 R1 基础交易步骤；`RegionManagementPage.tsx` 维护区域操作视图；`AdminConsolePage.tsx` 维护后台工作台。它们由 `App.tsx` 组合，不引入新的路由框架。

后台工作台按“总览、审核队列、工单、审计、权限”组织。运营管理员只获得业务队列、工单和自身授权只读能力；系统管理员额外获得策略同步、受控运维、审计导出审批和角色授权变更入口。区域管理员继续使用独立区域工作台，只能在 `regionScope` 中切换区域并处理该区域的审核、公告和工单。所有原型操作只更新页面本地演示状态，生产请求仍必须重新执行 Casbin、有效期、范围和二次验证裁决。

## 分期原型排期

| 周期 | 原型范围 | 验收重点 |
|---|---|---|
| R1 | 游客/VIP、学生认证、校园模式、三类移动管理入口、独立 PC 后台、商城基础交易与三类 RBAC 角色 | 游客仅预览；三类管理员只看到授权范围；基础下单和支付可恢复 |
| R2 | 物流、退款、售后和区域交易队列的权限状态 | 区域关闭后不阻断既有订单与售后；高风险资金操作需审批 |
| R3 | 多区域选择、授权到期、灰度和数据范围 | 角色或范围变更后立即拒绝旧范围操作 |
| R4 | 风险治理、永久封禁审批、人工复核和关闭开关 | 自动策略不能绕过人工复核，受限用户保留申诉与数据权利入口 |

## 验收标准

1. 原型可切换 R1-R4 与五类访问主体，且切换后页面能力与阶段一致。
2. 三类管理员可从客户端设置进入各自移动管理页，非管理用户没有入口并在直接访问时被拒绝。
3. 三类管理员可从独立 PC Web 后台进入相同权限范围的工作台，并共用 `qh_user` 演示身份。
4. 原型构建、类型检查和关键交互均通过；浏览器控制台无错误。
5. 后台审核可完成“筛选 -> 查看详情 -> 选择理由 -> 提交处置”的原型闭环；工单、审计导出和授权变更均表达审批或角色限制。
6. 区域管理员只能处理授权区域，运营管理员不能修改系统角色，系统管理员的高风险操作必须展示二次验证或审批前置状态。

## LOOP 原型验证闭环

最终验收采用 LOOP 闭环执行：以构建、角色切换、直接访问拒绝、区域范围、游客通知与商城预览、游客写操作拦截、R1 购物车/订单/支付状态、移动端管理、独立 PC 后台、悬浮球预置位、响应式布局和浏览器控制台为检查集合；任一检查失败即记录问题、修复受影响页面或会话规则、重新构建并复验受影响路径。只有全部检查通过且没有已知遗留问题，才可结束当前周期的原型验证。
