# 趣汇核心实体设计

## 1. 设计基准

- 数据库口径：Oracle；本文只定义逻辑类型、长度、精度、非空性、唯一性和业务关系。
- 主键统一由应用层生成；绝大多数聚合使用 `NUMBER(19)`，一对一从表沿用聚合键，已读游标使用组合主键；时间统一为 `TIMESTAMP(6)`。
- 金额统一保存为最小货币单位，使用 `NUMBER(19)`；数量使用 `NUMBER(10,2)`，人数使用 `NUMBER(5)`，经纬度使用 `NUMBER(10,7)`。
- 状态、类型和策略使用 `VARCHAR2` 枚举值；布尔值使用 `CHAR(1)`，取值 `Y/N`。所有持久化枚举的允许值、英文存储码和迁移原则统一以[趣汇枚举值字典](趣汇枚举值字典.md)为准。
- SQL 脚本不声明数据库外键；字段名保留 `_id` 关系语义，由领域服务、仓储和数据治理任务校验关系完整性。
- 不把所有历史写入一张“日志表”：领域状态变化保留在所属聚合的专用流水中，用户浏览与交互写入行为事件，后台及高风险业务操作写入不可变审计日志。

## 3. 关键关系与生命周期

1. `qh_user` 是账户根实体；身份、资料、偏好、会员和认证均按 `user_id` 关联。删除采用逻辑删除，历史订单、消息、帖子不因用户退出而物理删除。
2. `qh_post` 是正式社区内容的统一聚合根；每个帖子只落一张与 `post_type` 匹配的扩展表，地点、媒体、参与、留言、字段变更和状态流水是一对多。正式状态从审核中开始；审核被拒后保留拒绝状态并回填新草稿修改，不将正式帖子退回草稿。R2 拼单中 `qh_post_participant.payment_status` 仅是交易事件驱动的参与资格投影，必须保存结算、订单、来源事件和来源版本引用；订单、支付和退款事实唯一归交易域。
3. 帖子可关联一个活动群聊 `qh_chat_room.post_id`；私聊不关联帖子。群成员离开后保留成员历史；`qh_chat_message` 按 `room_id` 保存单调递增 `message_seq`、发送方 `client_message_id`、持久化/投递/确认状态和撤回状态，`qh_chat_member` 保存单调前进的确认/已读游标。`message_seq` 与游标用于 Netty 重连、跨节点投递失败和发布排空后的补拉，不以在线连接内存作为消息事实。
4. `qh_notification` 保存业务事件，`qh_user_notification` 保存收件人、已读和确认状态；同一通知可投递给多个用户。
5. 商品采用“商品 SPU + SKU”结构；用户转卖采用独立刊登实体。订单项按来源类型互斥关联自营 SKU 或转卖刊登：自营项填写 `product_id/sku_id`，转卖项只填写 `source_id`。订单保存名称、规格、价格和收货地址快照，确保后续内容修改不影响历史订单。
6. `qh_report` 通过 `target_type/target_id` 支持帖子、留言、用户、消息和商品治理；`qh_user_block` 控制用户消息和内容可见性。
7. 地点公开策略：列表和推荐只读取市区，市区缺失时使用街道；精确地点通过 `visibility_level` 在确认成员或发起人范围内展示。
8. 兑换码、邀请、收藏、评价和客服反馈均为独立历史实体；用户好评率由 `qh_user_review` 中审核有效的评价聚合，`qh_user_profile.good_rate` 仅作为查询缓存。商品评价继续由 `qh_product_review` 承载，不能与用户信用评价混用。
9. `qh_post_draft` 不复用 `qh_post`：草稿允许类型字段未填、精确地点未确认和多轮助手回填，首次发布校验通过后才拆分写入 `qh_post`、类型扩展、地点及媒体实体。审核被拒后的返修草稿以 `source_post_id` 关联原帖，重提时用乐观锁更新同一聚合。草稿载荷只服务编辑恢复，不用于列表筛选、统计或正式业务判断。
10. 趣汇小程序的自定义分类由 `qh_user_mini_program_group` 承载；`qh_user_mini_program.group_id`、可空 `sort_order` 和 `favorite_flag` 分别表达分组、显式组内顺序与收藏。`sort_order IS NULL` 表示用户尚未设置顺序，查询时排在显式排序值之后。
11. 分享链接由 `qh_share_link` 提供可归因的落地标识，后续的打开、授权、参与和下单通过 `qh_user_behavior_event.share_link_id` 关联；注册邀请仍使用 `qh_invitation`，两者不混用。

## 4. 系统设计校验矩阵

| 系统功能 | 主要实体 | 校验结论 |
|---|---|---|
| 登录、资料、账号安全 | `qh_user`、`qh_user_identity`、`qh_user_profile`、`qh_user_login_device` | 账户主体、绑定身份、公开资料和设备会话分离；支持注销后的历史留存。 |
| 隐私、通知、悬浮球反馈、校园版 | `qh_user_preference`、`qh_student_verification`、`qh_campus` | 位置精度、推荐、陌生人消息、系统/业务/聊天通知、音效/震动、免打扰和校园开关均有独立字段。 |
| 社区五类帖子 | `qh_post_draft`、`qh_post` + 五张扩展表 + 地点/媒体/参与/留言/状态流水 | 草稿与正式内容分离；公共字段与类型字段可查询；人数、参与、支付、状态和精确位置权限不混用。 |
| 分享、关注、收藏、举报、拉黑 | `qh_user_follow`、`qh_favorite`、`qh_report`、`qh_user_block` | 支持用户、帖子、商品等多对象关系；举报具备一次性提交和处理审计字段。 |
| 私聊、群聊、客服 | `qh_chat_room`、`qh_chat_member`、`qh_chat_message`、`qh_chat_message_media`、`qh_support_ticket` | 私聊/活动群聊区分；消息支持文本、图片、语音、业务卡片、失败、撤回、确认/已读游标与按 `message_seq` 离线补拉。 |
| 系统/业务通知和未读 | `qh_notification`、`qh_user_notification` | 通知内容与收件人已读/确认状态分离，业务关联可回到帖子或订单。 |
| 商城、支付、物流、售后、评价 | 商品、SKU、购物车、订单、支付、配送、售后、商品评价和用户评价实体 | 商品快照保证历史稳定；订单、支付、履约、售后与商品评价各自保留生命周期，用户评价可追溯到订单项或社区参与记录。 |
| 用户转卖 | `qh_user_listing`、`qh_user_listing_media`、订单来源字段 | 转卖订单项只关联刊登标识，自营商品标识保持为空；已覆盖成色、单价、可售数量、交付方式、媒体和订单闭环。议价、担保和票券核销等待具体规则后再扩展。 |
| 会员、签到、邀请、近邻配额、兑换码 | `qh_user_membership`、`qh_points_ledger`、`qh_invitation`、`qh_help_quota_monthly`、`qh_redeem_*` | 汇总余额与可追溯明细并存；按自然月配额和兑换失败原因可审计。 |
| 推荐、负反馈、趣汇小程序 | `qh_content_event`、`qh_content_feedback`、`qh_mini_program`、`qh_user_mini_program` | 曝光转化、负反馈、收藏和查询时间均有承载；可空排序值可区分未排序与显式顺序。 |
| 原型草稿与搜索 | `qh_post_draft`、`qh_user_search_history` | 助手/社区表单可保存不完整草稿；最近搜索可按用户、范围去重、计数和清空，热门词由行为事件离线聚合。 |
| 分享进入与转化 | `qh_share_link`、`qh_user_behavior_event` | 帖子和商品分享有稳定分享码；可串联分享创建、落地、授权、参与和下单，不用注册邀请码替代业务分享。 |
| 用户行为分析 | `qh_content_event`、`qh_user_behavior_event`、`qh_content_feedback` | 推荐曝光/反馈保留专用低耦合模型；页面浏览、搜索、筛选、收藏、分享、发布草稿、参与、支付等以统一事件名和属性上报。 |
| 运营与敏感操作审计 | `qh_operation_audit_log` + 专用领域流水 | 审核举报/客服工单/订单处置/账号与权限等操作记录操作者、目标、结果、请求链路与脱敏前后快照；帖子与订单状态仍分别使用专用变更流水。 |

校验结论：首期产品文档及原型中已明确的账户、社区、消息、商城、会员、校园、推荐、治理、草稿、搜索、小程序布局和分享进入能力均有实体承载；业务统计、用户行为分析与高风险操作也具备独立数据源。仍需在应用服务层实现状态机、权限、跨表一致性、库存并发、事件脱敏与敏感信息脱敏，不能仅依赖本脚本的字段约束。

## 5. 必填与校验原则

- 公共帖子必须有作者、类型、标题、状态、可见范围、主时间、截止时间和人数上下限；近邻互助正文必填。
- `min_participants <= max_participants`，确认人数不得超过最大人数；拼车和线上开黑不得以单一固定人数替代上下限。
- 金额为非负整数最小货币单位；固定收费模式才要求填写金额；支付、退款、订单和参与状态分别维护。
- 认证状态、校园可见范围、通知已读、消息发送和商品库存均使用独立字段，禁止把多个业务状态压缩到一个枚举。
- 商品订单必须保留价格、规格、地址和配送快照；发货单、物流节点、售后单和评价分别记录，避免订单主状态承担全部履约历史。
- 订单项来源必须互斥：`PRODUCT_SKU` 只允许 `product_id/sku_id`，`USER_LISTING` 只允许 `source_id`；不得为兼容非空字段伪造商品或 SKU。
- 用户评价必须关联真实订单项或社区参与记录；同一评价人、被评价人和业务关系只能产生一条有效评价。用户资料中的好评率不得脱离评价事实直接修改。
- 好评率口径为审核有效且 `rating >= 4` 的用户评价数除以审核有效用户评价总数，结果按百分比缓存到 `qh_user_profile.good_rate`；无有效评价时保存为空，不显示伪造的 100%。
- 脚本中的 `CHECK` 约束只做字段级安全校验；跨表、状态机和权限校验由应用服务完成。

## 6. 日志、统计与分析架构

### 6.1 三层事实模型

| 层级 | 实体 | 写入时机 | 主要用途 | 不承担的职责 |
|---|---|---|---|---|
| 领域事实 | `qh_post_change_log`、`qh_post_status_log`、`qh_order_status_log`、`qh_points_ledger`、`qh_order_delivery_event` 等 | 聚合状态、业务字段或权益发生变化时，与业务事务同一一致性边界写入。 | 状态回溯、争议处理、业务统计和补偿。 | 不记录每次页面浏览、筛选或点击。 |
| 行为事实 | `qh_content_event`、`qh_user_behavior_event`、`qh_content_feedback` | 推荐曝光、页面访问、搜索、筛选、分享、点击及转化时异步批量写入。 | 漏斗、留存、内容效果、归因与推荐训练。 | 不作为订单、参与、积分或权限的唯一依据。 |
| 操作审计 | `qh_operation_audit_log` | 运营后台、客服、审核、风控及敏感用户操作成功或拒绝时写入。 | 责任追溯、合规审计、异常排查和后台操作统计。 | 不替代领域状态流水，也不写入高频浏览行为。 |

### 6.2 事件边界与数据治理

- `qh_content_event` 继续只承载推荐候选的曝光、点击和转化，并保留推荐位与筛选快照；通用页面和业务行为统一写入 `qh_user_behavior_event`，避免推荐上下文成为所有事件的必填条件。
- 行为事件至少规范 `page_view`、`search_submit`、`filter_apply`、`content_open`、`favorite_toggle`、`share_create`、`share_open`、`draft_save`、`post_publish`、`participation_apply`、`payment_submit`、`payment_result`。事件属性仅放可演进的非核心维度，核心关联必须使用独立列。
- `user_id` 允许为空以支持游客，匿名访问必须写 `anonymous_id`；登录合并、会话归因及分享归因由分析服务处理，不能通过更新历史事件覆盖原始身份。
- `qh_user_behavior_event` 为高写入量事实表，生产环境按 `occurred_at` 做月度范围分区，并设置热数据在线、冷数据归档和删除期限；DDL 目前不固化分区策略，避免在尚未确认容量前锁死运维方案。
- 审计快照和行为属性不得保存密码、证件原文、完整手机号、支付凭据、精确住址或语音原始内容；保存前执行字段白名单、掩码或哈希。`client_ip_hash` 只用于安全关联，不保存原始 IP。
- 分析报表由离线/实时数仓消费事件和领域流水构建；交易金额、成交量、退款率等经营指标以订单、支付、售后和状态流水为准，不从埋点反推。

### 6.3 应用层写入规则

1. 发布帖子：草稿校验通过后创建正式帖子并写入从空状态到审核中的 `qh_post_status_log`；后续业务字段变化写 `qh_post_change_log`。事务提交后投递 `post_publish` 行为事件，失败不产生“发布成功”事件。
2. 订单状态、积分、认证和举报处置：写入对应专用领域流水，再按需要写 `qh_operation_audit_log`；同一 `request_id` 用于跨服务排查。
3. 搜索、筛选、浏览和推荐曝光：不阻塞主请求；采用可靠异步投递、批量落库与幂等事件 ID。行为写入失败不得影响用户浏览，但必须有失败监控和补偿队列。
4. 审计日志仅追加，禁止业务接口更新或物理删除；访问权限按最小授权控制，并记录审计查询本身。
