# 趣汇核心实体设计

## 1. 设计基准

- 数据库口径：Oracle；本文只定义逻辑类型、长度、精度、非空性、唯一性和业务关系。
- 主键统一由应用层生成；绝大多数聚合使用 `NUMBER(19)`，一对一从表沿用聚合键，已读游标使用组合主键；时间统一为 `TIMESTAMP(6)`。
- 金额统一保存为最小货币单位，使用 `NUMBER(19)`；数量使用 `NUMBER(10,2)`，人数使用 `NUMBER(5)`，经纬度使用 `NUMBER(10,7)`。
- 状态、类型和策略使用 `VARCHAR2` 枚举值；布尔值使用 `CHAR(1)`，取值 `Y/N`。
- SQL 脚本不声明数据库外键；字段名保留 `_id` 关系语义，由领域服务、仓储和数据治理任务校验关系完整性。

## 2. 实体分组与职责

| 分组 | 实体 | 职责 |
|---|---|---|
| 账户与身份 | `qh_user`、`qh_user_identity`、`qh_user_profile`、`qh_user_preference`、`qh_user_login_device` | 登录主体、第三方/手机号身份、公开资料、隐私/通知/悬浮球偏好和登录设备。 |
| 校园与权益 | `qh_campus`、`qh_student_verification`、`qh_user_membership`、`qh_points_ledger`、`qh_help_quota_monthly` | 校园版过滤、认证、VIP、积分流水和近邻互助月度配额。 |
| 关系与位置 | `qh_user_follow`、`qh_user_block`、`qh_user_address`、`qh_favorite` | 关注、拉黑、商城履约地址和社区/商品收藏。 |
| 内容与社区 | `qh_post`、五类帖子扩展、`qh_post_location`、`qh_post_media`、`qh_post_participant`、`qh_post_change_log`、`qh_post_comment`、`qh_report` | 帖子生命周期、结构化类型字段、地点隐私、媒体、参与、留言回复和治理。 |
| 沟通与通知 | `qh_chat_room`、`qh_chat_member`、`qh_chat_message`、`qh_chat_message_media`、`qh_chat_read_cursor`、`qh_notification`、`qh_user_notification` | 私聊/活动群聊、文本/图片/语音消息、消息状态、已读游标、系统通知和业务通知。 |
| 商城交易 | `qh_product_category`、`qh_product`、`qh_product_sku`、`qh_product_media`、`qh_user_listing`、`qh_user_listing_media`、`qh_cart_item`、`qh_order`、`qh_order_item`、`qh_payment`、`qh_order_status_log`、`qh_order_delivery`、`qh_order_delivery_event`、`qh_after_sale`、`qh_product_review` | 自营商品、用户转卖刊登、规格库存、订单、支付、发货履约轨迹、售后和评价。 |
| 推荐与运营 | `qh_content_event`、`qh_content_feedback`、`qh_mini_program`、`qh_user_mini_program`、`qh_invitation`、`qh_redeem_code`、`qh_redeem_record`、`qh_support_ticket` | 曝光/点击/转化埋点、负反馈、趣汇小程序、邀请、兑换码和帮助客服反馈。 |

## 3. 关键关系与生命周期

1. `qh_user` 是账户根实体；身份、资料、偏好、会员和认证均按 `user_id` 关联。删除采用逻辑删除，历史订单、消息、帖子不因用户退出而物理删除。
2. `qh_post` 是社区统一聚合根；每个帖子只落一张与 `post_type` 匹配的扩展表，地点、媒体、参与、留言和变更日志是一对多。`qh_post_participant.payment_status` 与帖子状态、参与状态独立。
3. 帖子可关联一个活动群聊 `qh_chat_room.post_id`；私聊不关联帖子。群成员离开后保留成员历史，消息使用发送状态和撤回状态表达。
4. `qh_notification` 保存业务事件，`qh_user_notification` 保存收件人、已读和确认状态；同一通知可投递给多个用户。
5. 商品采用“商品 SPU + SKU”结构；用户转卖采用独立刊登实体。订单项按来源类型关联自营 SKU 或转卖刊登，并保存名称、规格、价格和收货地址快照，确保后续内容修改不影响历史订单。
6. `qh_report` 通过 `target_type/target_id` 支持帖子、留言、用户、消息和商品治理；`qh_user_block` 控制用户消息和内容可见性。
7. 地点公开策略：列表和推荐只读取市区，市区缺失时使用街道；精确地点通过 `visibility_level` 在确认成员或发起人范围内展示。
8. 兑换码、邀请、收藏、评价和客服反馈均为独立历史实体；不能用用户汇总字段替代明细，否则无法重放权益、撤销奖励或审计处理过程。

## 6. 系统设计校验矩阵

| 系统功能 | 主要实体 | 校验结论 |
|---|---|---|
| 登录、资料、账号安全 | `qh_user`、`qh_user_identity`、`qh_user_profile`、`qh_user_login_device` | 账户主体、绑定身份、公开资料和设备会话分离；支持注销后的历史留存。 |
| 隐私、通知、悬浮球反馈、校园版 | `qh_user_preference`、`qh_student_verification`、`qh_campus` | 位置精度、推荐、陌生人消息、系统/业务/聊天通知、音效/震动、免打扰和校园开关均有独立字段。 |
| 社区五类帖子 | `qh_post` + 五张扩展表 + 地点/媒体/参与/留言 | 公共字段与类型字段可查询；人数、参与、支付、状态和精确位置权限不混用。 |
| 分享、关注、收藏、举报、拉黑 | `qh_user_follow`、`qh_favorite`、`qh_report`、`qh_user_block` | 支持用户、帖子、商品等多对象关系；举报具备一次性提交和处理审计字段。 |
| 私聊、群聊、客服 | `qh_chat_room`、`qh_chat_member`、`qh_chat_message`、`qh_chat_message_media`、`qh_support_ticket` | 私聊/活动群聊区分；消息支持文本、图片、语音、业务卡片、失败、撤回和离线收口。 |
| 系统/业务通知和未读 | `qh_notification`、`qh_user_notification` | 通知内容与收件人已读/确认状态分离，业务关联可回到帖子或订单。 |
| 商城、支付、物流、售后、评价 | 商品、SKU、购物车、订单、支付、配送、售后、评价实体 | 商品快照保证历史稳定；订单、支付、履约、售后、评价各自保留生命周期。 |
| 用户转卖 | `qh_user_listing`、`qh_user_listing_media`、订单来源字段 | 已覆盖用户闲置/权益刊登、成色、单价、可售数量、交付方式、媒体和订单闭环；议价、担保和票券核销等待具体规则后再扩展。 |
| 会员、签到、邀请、近邻配额、兑换码 | `qh_user_membership`、`qh_points_ledger`、`qh_invitation`、`qh_help_quota_monthly`、`qh_redeem_*` | 汇总余额与可追溯明细并存；按自然月配额和兑换失败原因可审计。 |
| 推荐、负反馈、趣汇小程序 | `qh_content_event`、`qh_content_feedback`、`qh_mini_program`、`qh_user_mini_program` | 曝光转化、负反馈撤销、收藏排序和查询时间均有承载。 |

校验结论：首期产品文档中已明确的账户、社区、消息、商城、会员、校园、推荐和治理能力均有实体承载；仍需在应用服务层实现状态机、权限、跨表一致性、库存并发和敏感信息脱敏，不能仅依赖本脚本的字段约束。

## 4. 必填与校验原则

- 公共帖子必须有作者、类型、标题、状态、可见范围、主时间、截止时间和人数上下限；近邻互助正文必填。
- `min_participants <= max_participants`，确认人数不得超过最大人数；拼车和线上开黑不得以单一固定人数替代上下限。
- 金额为非负整数最小货币单位；固定收费模式才要求填写金额；支付、退款、订单和参与状态分别维护。
- 认证状态、校园可见范围、通知已读、消息发送和商品库存均使用独立字段，禁止把多个业务状态压缩到一个枚举。
- 商品订单必须保留价格、规格、地址和配送快照；发货单、物流节点、售后单和评价分别记录，避免订单主状态承担全部履约历史。
- 脚本中的 `CHECK` 约束只做字段级安全校验；跨表、状态机和权限校验由应用服务完成。
