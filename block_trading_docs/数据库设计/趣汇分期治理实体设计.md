# 趣汇分期治理实体设计

## 1. 设计范围

本文是对[趣汇核心实体设计](趣汇核心实体设计.md)和[趣汇帖子领域实体设计](帖子领域实体设计.md)的增量设计，按 `R1-R4` 的发布周期定义治理、运营、可见性、交易履约和规模化能力所需实体。已有的账户、帖子、订单、支付、配送、售后、评价、消息、举报、拉黑和客服实体继续复用，不重复建表。

数据库仍以 Oracle 为准：主键使用 `NUMBER(19)`，业务时间使用 `TIMESTAMP(6)`，状态和类型使用 `VARCHAR2` 枚举，布尔值使用 `CHAR(1)` 的 `Y/N`。SQL 不声明数据库外键，`*_id` 只表达关系语义；跨聚合完整性、状态机和权限由应用服务保证。

## 2. 分期总览

| 发布期 | 新增实体主题 | 依赖的既有实体 |
|---|---|---|
| R1 | 区域运营、后台 RBAC、三段审核、校园/拉黑可见性、未成年人/安全事件、规则版本、跨期上下文、数据资产、风险事件与事件 Outbox | `qh_user`、`qh_user_preference`、`qh_campus`、`qh_student_verification`、`qh_user_block`、`qh_post`、`qh_post_comment`、`qh_report`、`qh_notification`、`qh_support_ticket` |
| R2 | 自营交易对账、商品合规、区域可售/库存、服务路由、库存预占、订单经营快照、物流节点异常、履约工单、售后证据、关键通知送达、评价申诉 | `qh_order`、`qh_order_item`、`qh_payment`、`qh_order_delivery`、`qh_order_delivery_event`、`qh_after_sale`、`qh_product_review`、R1 跨期上下文与事件实体 |
| R3 | 区域经营健康度、数据主体请求、数据保留、备份恢复与演练、触达送达、实验曝光、法律保留、权益账本 | R1/R2 的审计、区域、工单、通知、业务事件、数据资产和交易快照 |
| R4 | 封禁分级、关联反欺诈、模型决策审计、侵权投诉与反通知、规模化权益策略 | R1-R3 的用户、订单、内容、审核、工单、风险、实验、法律保留、权益账本和审计实体 |

### 3.2 帖子与举报三段审核链

`qh_report` 仍是用户举报事实，不将三个审核环节塞入其单行状态。帖子提交和举报都创建 `qh_review_case`；一个审核案可关联一个主对象及多个证据，并有严格的阶段流水。

| 实体 | 核心字段 | 说明与约束 |
|---|---|---|
| `qh_review_case` | `id`、`case_no`、`source_type`、`source_id`、`target_type`、`target_id`、`author_id`、`region_id`、`priority`、`case_status`、`final_decision`、`final_reason_code`、`finalized_by`、`finalized_at`、`appeal_status`、审计时间 | `source_type` 为 `POST_SUBMIT`、`REPORT`、`SYSTEM_SCAN`；`target_type` 支持帖子、留言、回复、商品、用户、消息。帖子审核与举报审核共用，但来源不可丢失。 |
| `qh_review_stage` | `id`、`case_id`、`stage_type`、`stage_status`、`rule_version`、`model_version`、`input_digest`、`decision`、`risk_level`、`reason_codes_json`、`operator_type`、`operator_id`、`started_at`、`completed_at` | 阶段按 `RULE_MATCH`、`MODEL_REVIEW`、`HUMAN_REVIEW` 顺序创建；人工阶段才能写入最终公开、驳回、下架或恢复结论。高危规则/模型结果只允许写临时措施。 |
| `qh_review_rule_set` | `id`、`rule_set_code`、`version_no`、`scene_type`、`region_id`、`rule_digest`、`config_uri`、`status`、`effective_at`、`retired_at`、`approved_by`、审计时间 | 内容审核和反滥用规则集版本；审核阶段保存 `rule_set_id` 快照引用，不直接依赖可变配置。 |
| `qh_model_version` | `id`、`model_code`、`version_no`、`provider_code`、`scene_type`、`prompt_digest`、`config_digest`、`status`、`effective_at`、`retired_at`、`approved_by`、审计时间 | 模型治理领域唯一拥有的大模型审核、推荐和风控模型版本注册；不保存密钥，调用阶段引用固定版本，业务领域只保存自身决策记录与人工覆盖。 |
| `qh_review_evidence` | `id`、`case_id`、`evidence_type`、`source_uri`、`content_digest`、`metadata_json`、`collected_by_type`、`collected_by_id`、`created_at` | 保存规则命中、图片识别、举报说明、物流/订单/聊天快照等证据引用；原文敏感数据由对象存储和权限服务保护。 |
| `qh_content_temporary_action` | `id`、`case_id`、`target_type`、`target_id`、`action_type`、`action_status`、`trigger_stage_id`、`effective_at`、`expires_at`、`released_at`、`released_by` | 规则或模型命中高危时的临时下架、隐藏、停止报名等措施；不能替代 R4 的账号封禁处置。 |
| `qh_review_appeal` | `id`、`case_id`、`appellant_user_id`、`appeal_reason`、`evidence_json`、`status`、`handled_by`、`handled_at`、`result_note`、审计时间 | 复用用户侧申诉入口；同一审核案只允许一个未关闭申诉。 |

### 3.3 可见性、拉黑与反滥用

| 实体 | 核心字段 | 说明与约束 |
|---|---|---|

| `qh_visibility_access_log` | `id`、`request_id`、`viewer_id`、`target_type`、`target_id`、`decision`、`decision_reason`、`campus_id_snapshot`、`region_id_snapshot`、`created_at` | 仅记录被拒绝或抽样成功的可见性决策，用于权限排障与审计；不记录完整内容正文。 |
| `qh_risk_challenge` | `id`、`user_id`、`device_id`、`scene_type`、`risk_level`、`challenge_type`、`challenge_status`、`expires_at`、`passed_at`、`failure_reason`、审计时间 | 信任安全领域拥有的注册、登录、发帖、举报、私信、邀请等场景验证码、二次验证或人工复核挑战；不能以单一设备标识决定最终处罚。 |
| `qh_security_incident` | `id`、`incident_no`、`incident_type`、`severity`、`region_id`、`reported_by_type`、`reported_by_id`、`status`、`commander_admin_id`、`started_at`、`contained_at`、`resolved_at`、`summary` | 信任安全领域拥有的账号盗用、诈骗、人身安全、隐私泄露、重大内容风险事件；关联工单、临时措施和用户通知，区域应急路由由区域策略领域提供。 |
| `qh_user_age_verification` | `id`、`user_id`、`age_band`、`minor_flag`、`verification_method`、`verification_status`、`verified_at`、`expires_at`、`evidence_digest`、审计时间 | 仅保存最小化年龄段和验证结果，不默认保存完整出生日期；同一用户只允许一个当前有效结果。 |
| `qh_guardian_consent` | `id`、`minor_user_id`、`guardian_identity_ref`、`consent_scope`、`consent_status`、`consented_at`、`revoked_at`、`evidence_digest`、审计时间 | 需要监护授权的功能范围与撤回历史；监护人敏感身份保存为受控引用或摘要。 |

| `qh_user_policy_consent` | `id`、`user_id`、`policy_version_id`、`consent_action`、`occurred_at`、`client_type`、`request_id`、`supersedes_consent_id` | 追加式保存 `ACCEPT`、`WITHDRAW` 等动作，不更新覆盖历史确认；撤回记录指向被替代的同意记录。 |

**R1 复用与扩展：** `qh_user_block` 保持单向写入，但所有读取和写入服务都以任意方向存在有效拉黑记录为“双向隔离”条件；为 `(user_id, blocked_user_id, status)` 建索引。`qh_post`、`qh_post_comment`、`qh_user_profile` 不新增“可见”冗余字段，统一由可见性策略、校园范围和拉黑关系计算。

## 4. R2：单区域公开交易实体

**R1/R2 -> R3 前置约束：** R2 订单、支付、退款、库存、配送、售后和通知必须固化区域、策略、责任路由和时效阈值快照；商品可售、库存、配送范围和营业时间必须有版本化生效/回滚事实，不能只放在 R1 的通用区域策略 JSON 中。

## 7. 跨期关系、索引与落地顺序

### 关系约束

1. `qh_review_case` 与 `qh_report`、`qh_post`、`qh_post_comment` 等对象通过多态目标关联；阶段流水不可物理删除，最终结论必须可追溯至人工阶段。
2. 可见性策略不持久化为“允许访问名单”。`qh_user_block`、校园认证、帖子范围和区域策略是事实来源，`qh_visibility_invalidation_task` 只负责清理派生索引和缓存。
3. `qh_delivery_exception`、`qh_fulfillment_work_order`、`qh_after_sale` 与 `qh_support_ticket` 可互相引用，但订单状态仍以 `qh_order` 和 `qh_order_status_log` 为准；物流事件不得回退已确认节点。
4. `qh_account_enforcement_case` 只限制用户生成内容和互动能力；订单履约、退款/售后、申诉、隐私数据和注销必须保持服务访问。
5. R1/R2/R3 产生的业务事实、媒体、风险、实验和权益记录只追加或通过独立扩展表关联；R4 不回写覆盖早期主实体状态，所有自动化决策必须引用策略/模型版本并保留人工覆盖。

### 实施校验

- R1 先交付区域、RBAC、审核链、可见性失效、安全事件和规则版本实体；审核、搜索、推荐、详情、深链、通知分发都必须使用同一可见性服务。
- R1 同步交付跨期上下文快照、数据资产、风险事件、客服工单事件和事务事件 Outbox；不开放交易，但这些实体必须覆盖社区、参与、客服、通知、区域准入和后台操作。
- R2 在真实收款前交付支付回调、对账、商品合规、物流异常、履约工单、售后证据和关键通知送达实体；未满足时只允许浏览和意向收集。
- R2 同步交付区域服务路由、区域 SKU 可售/库存、库存预占和订单经营快照；真实支付、退款和履约事实必须引用 R1 上下文与事件幂等契约。
- R3 扩区域前完成数据主体请求、留存策略、备份恢复演练、区域健康度和实验实体。
- R3 同步交付实验实际曝光、对象级法律保留和会员/积分权益账本；指标和实验不得用当前配置覆盖历史决策。
- R4 在有足够审计数据后再启用封禁分级、关联图谱、模型审计和侵权处理；所有自动处置均保留人工复核和关闭开关。
