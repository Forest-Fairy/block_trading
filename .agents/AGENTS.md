# 项目规则

## 项目特色规则入口
`../PROJECT.md`

## 编码实现规则

- 避免过度封装, 优先在当前业务域内直接表达流程, 并且只有出现明确复用价值时再提取公共方法。
- 允许参考原有代码进行方法封装, 但不改参考代码去复用新封装方法。
- 单个类中的方法嵌套调用层级不得超过 3 层，避免为了抽象流程而形成过深调用链；若超过 3 层，应优先回到当前业务域内收敛表达。
- 参数设计尽可能扁平化, 避免为了单次调用引入层级过深的包装对象。
- 对相关流程化的业务需求的开发必须补充注释, 尤其是状态变化、前置校验、异步处理收口、初始化等关键链路。
- 当代码存在多个方法嵌套调用时, 入口方法和关键中转方法都必须说明上下游关系与业务意图, 避免只看方法名无法理解流程。
- 在 service 业务类中使用 repository 对象时, 不要使用基类提供的查询构造器的方法(如 lambdaQuery, lambdaUpdate 等orm框架提供的方法), 需要使用具体接口封装的方法, 不存在就创建.
- 代码中已有的注释不要随意删除, 通常需要参考注释的说明编写代码, 除非与相关要求有矛盾点, 需要补充注释进行说明.
- 在service业务类中, 从数据库查询数据的方法要用 query?InDb 命名.
- 新增或修改方法签名时, 若参数列表较长需要换行, 应从第一个参数的起始位置整体换行并保持参数缩进一致; 不要把第一个参数留在方法名同一行后再从第二个参数开始换行; 同时避免一参一行, 应在行宽允许时将多个参数保留在同一行, 仅当单个参数声明本身过长时才允许该参数单独占行; 不因该规则主动批量调整历史代码.
- 引用方法时, 若传入固定参数, 需要使用注释说明调用方法的目的以及在此处使用静态参数的原因和作用

## 代码审查规则
- 代码方法参数列表或参数含义进行变动时, 需要审查对应参数及参数带出的相关对象的使用逻辑是否存在问题.
- 条件判断类的代码, 需要注意判别的对象是否与相关参数的含义或其他相关判断存在冲突.

## 文档规则

- 项目开发相关输出必须使用中文。
- 一旦进入项目开发任务, 必须同步维护文档, 不能只改代码不补文档(维护的文档必须在文档对应目录下, 并且绝不是README文档)。
- 文档分类分为 `产品文档` 与 `业务开发文档` 两类。
- 产品文档按 `scope` 分层维护, 这里的 `scope` 固定为 `项目文档 -> 功能文档 -> 模块文档`。
- 业务开发文档按 `scope` 分层维护, 这里的 `scope` 固定为 `业务需求文档 -> 业务功能文档 -> 业务模块文档`。

### 文档入口规则

- 文档入口说明统一维护在 `PROJECT.md`, 不分散写在其他规则文档中。
- 项目说明文档固定指 `PROJECT.md`, 只承载项目级说明信息, 不承载通用流程规则。
- `PROJECT.md` 只维护当前项目特有且相对稳定的信息, 例如项目范围、文档入口、原型入口、模块边界入口。
- `PROJECT.md` 中的文档入口必须分开说明 `产品文档` 与 `业务开发文档`, 避免混写。
- 通用协作流程、文档写法、状态流转、智能体分工等规则统一维护在 `AGENTS.md`, 不在 `PROJECT.md` 重复展开。
- `PROJECT.md` 应保持简洁, 只作为当前项目的入口和索引, 不展开大段需求正文、实现细节或阶段性讨论。

### 业务开发文档导航规则

- 业务开发文档的具体目录以 `PROJECT.md` 中的业务开发文档入口为准, 并按 `{scope}/{title}.md` 单文件承载, 不创建导航文件。
- 业务开发文档不承担 `navigator.csv` 式导航职责, 其导航基线由相关产品文档与文件头人工补充的业务细节共同构成。
- 业务需求文档承载对需求的描述、功能概括以及对业务功能文档的导航。
- 业务功能文档承载对功能对应需求的概括以及对下级业务模块文档的导航。
- 业务需求文档和业务功能文档可在正文中维护必要的下行入口, 但这些入口仅作为阅读引导, 不替代产品文档导航链。
- 业务模块文档在正文内维护接口信息, 具体格式与范围遵循下文“功能接口格式规则”。
- 新增业务开发文档或迁移既有业务开发文档时, 直接编写或更新对应的 `{title}.md`。
- 基于业务开发文档执行开发任务时, 开发阶段只维护业务开发文档, 不要求同步调整产品文档。
- 业务开发完成后, 必须对业务开发文档进行归档梳理, 将已稳定的实现信息迁移到对应的新模块或目标产品文档中, 并整理为双文件承载结构。

### 产品文档导航规则

- 产品文档是指 `PROJECT.md` 中产品文档入口下的项目文档、功能文档和模块文档。
- 产品文档按 `{scope}/{title}/content.md + {scope}/{title}/navigator.csv` 双文件承载。
- 产品文档导航必须遵循 `上层文档 -> 下层 navigator.csv -> 下层 content.md` 的方式定位, 不得跳过导航链直接通读全量正文。
- 产品模块文档中的接口信息必须在正文中维护, 具体格式与范围遵循下文“功能接口格式规则”。
- `navigator.csv` 的字段、摘要规则、增量刷新方式和 `doc-navigator` 的使用约束, 继续沿用现有双文件规则。
- 新增或迁移产品文档时, 必须先编写或更新 `content.md`, 再刷新 `navigator.csv` 及相关摘要信息。
- 基于产品文档执行开发任务时, 开发结果必须回归到对应产品文档中, 并同步更新导航文件及相关摘要。
- 项目开发完成后, 必须及时将结果补充到对应文档中。

### 功能接口格式规则

- 业务模块文档和产品模块文档接口信息统一维护在模块文档的 `## 功能接口` 下。
- 业务模块文档中的 `## 功能接口` 只维护当前业务需求新增或改动且与当前业务直接相关的接口信息。
- 产品模块文档中的 `## 功能接口` 只维护产品现有已生效的功能接口信息, 不要求在业务开发阶段同步维护当前业务草案接口。
- `## 功能接口` 下按实际存在情况维护三级标题:
  - `### 启动参数`: 参数信息列表字段固定为 `参数英文, 参数中文, 类型, 作用, 取值示例`
  - `### 控制台接口`: 信息列表字段固定为 `命令名, 命令, 参数及说明, 对应代码文件和方法名, 调用示例`
  - `### web 接口`: 接口信息列表字段固定为 `接口名, 接口路径, 接口类型, 参数及说明, 对应的代码文件和方法名, 参数示例, 返回值示例`

## 上下文读取规则

- 当前上下文入口仅作为导航索引, 不代表必须阅读全文。
- 开始读取文档前, 必须先判断当前任务是以业务开发文档为基线, 还是以产品文档为基线, 再选择对应导航方式。
- 以业务开发文档为基线时, 必须先根据 `PROJECT.md` 中的业务开发文档入口定位对应的 `{title}.md`, 再按 `业务需求文档 -> 业务功能文档 -> 业务模块文档` 的正文入口逐层定位, 并结合人工补充的业务细节进行开发。
- 以产品文档为基线时, 必须先根据 `PROJECT.md` 中的产品文档入口定位上层文档, 再按 `上层文档 -> 下层 navigator.csv -> 下层 content.md` 的方式逐层定位目标片段。
- 用户指定文件、标题、关键字、段落或行号时, 只允许读取指定范围及其上下各 20 行。
- 用户未指定范围时, 必须先通过目录、标题或关键字检索定位候选位置, 再读取最相关片段。
- 首次读取单个文档正文时, 默认不超过一个标题块或 200 行。
- 仅当当前片段不足以判断直接上下游关系时, 才允许扩读直接上游一层和直接下游一层。
- 每次扩读前都必须先说明扩读原因。
- 读取完成后只保留与当前任务直接相关的摘要, 不保留无关细节。
- 当前迭代看板默认只读取任务摘要、当前状态、阻塞项和下一步, 不默认阅读全文。
- 当前迭代看板属于会话态数据, 必须存放在 `.agents/{session_name}_{SESSION_ID}/current-iteration-board.md`, 不得长期保存在固定规则目录根下。

## 智能体与人工协作

### 协作说明
智能体在用户请求生成业务需求文档以后, 人工可在需求文档 `{title}.md` 文件头补充业务需求细节说明。该补充说明区域不属于正式文档正文结构。

- 无状态表示尚未开始处理。
- `--R` 表示该段细节已被阅读、分析、跟进或正在处理中, 但尚未完成对应业务闭环。
- `--OK` 表示该段细节对应的业务需求已经明确完成开发, 且已完成与本轮任务匹配的验证、验收或必要文档回写, 后续智能体可将其视为完成标记。
- 仅执行进度检查、现状调研、代码阅读、影响分析、方案讨论、问题排查等非完成态动作时, 不得新增或改写 `--OK`; 若已阅读但未闭环, 只能保持或补充 `--R`。

### 协作流程
1 人工在业务需求细节补充说明区域顶部补充文本说明
2 智能体开始处理前先查找首个 `--OK`, 若存在则只读取文件开头到首个 `--OK` 之前的内容
3 若不存在 `--OK`, 则读取文件开头到首个以 `# 需求文档` 开头的标题行之前的内容
4 若首个以 `# 需求文档` 开头的标题行位于文件前 3 行内, 则表示该需求文档没有业务需求细节补充说明
5 智能体首次阅读、分析或跟进某段说明时, 在该段说明上一行补充 `--R`; 若该段原本已存在 `--R`, 则保持不变
6 仅当对应业务细节已经完成本轮开发、修复、配置调整或正式文档回写等目标, 且已完成与任务类型匹配的验证后, 才允许将该段前的 `--R` 改成 `--OK`
7 当任务只是检查当前业务开发进度、核对状态、做差异分析或给出建议时, 读取和反馈后必须保持原状态; 未完成的内容不得改成 `--OK`
8 若无法确认对应细节是否已真正完成, 默认保持 `--R` 或无状态, 不得猜测性标记 `--OK`


## 产品前置材料要求
- 纯后端开发任务不强制原型, 但必须先提供相应需求文档。
- 涉及前端开发、页面、客户端、显示、交互、动画或状态表达的任务, 必须先提供原型截图和交互说明。
